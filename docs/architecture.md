## 二、关键技术选型与决策

| 模块 / 需求 | 传统方案 | CodeGate 选型决策 | 决策收益与理由 |
| :--- | :--- | :--- | :--- |
| **编程语言** | Python / Node.js / Java | **Go 1.22+** | 高并发性能卓越、天然原生 Goroutine、内存开销极低（数十兆即可高并发运行）。 |
| **Web 框架** | Kong / APISIX / FastAPI | **Gin Web Framework** | 成熟稳定，中间件生态健全，轻量且吞吐能力出众。 |
| **底层持久化** | MySQL / PostgreSQL / Redis | **纯 Go SQLite (`modernc.org/sqlite`)** | **零外部中间件依赖**。无 CGO 动态依赖，支持跨平台编译为单二进制，彻底摆脱外部数据库运维。 |
| **缓存架构** | 外部 Redis 实例 | **内存滑动窗口 + LRU 缓存 + 原子计数** | 极低系统延迟（纳秒级内存读取），通过批量写保证高并发下 SQLite 无锁冲突。 |
| **前端架构** | 独立 Nginx 托管 React/Vue | **Go `embed.FS` 原生内嵌 React 产物** | **单二进制交付**。部署只需复制一个二进制程序与配置文件即可运行，极大降低交付 TCO。 |
| **配置同步** | 依赖配置中心 (Nacos/Consul) | **本地 YAML + 内存热加载订阅发布** | 进程级毫秒热更新，修改配置不重启进程、不断开长连接。 |

## 三、流量调度算法深度剖析

### 1. KV Cache 亲和性会话粘性路由（HRW 哈希）

#### 痛点
在多轮对话交互中，如果用户的连续交互请求被简单轮询分发到不同后端节点，各物理节点每次都要重新预热全量 Prompt 历史，不仅首字响应延迟（TTFT）大幅飙升，还白白耗费推理卡宝贵的显存算力。

#### HRW (Highest Random Weight / Rendezvous Hashing) 算法原理
为解决传统一致性哈希在后端节点伸缩时可能导致的雪崩问题，CodeGate 采用 HRW 算法进行会话粘性计算：

1. **会话标识提取**：优先从 HTTP 请求头提取 `X-Session-ID`、`X-Conversation-ID` 等，若缺失则从请求 Body 中解析 `session_id` 等字段；
2. **权重评分计算**：对于每个健康的候选后端实例 $B_i$，结合会话标识 $S$ 和实例唯一标识计算哈希权重分数：
   $$\text{Score}(S, B_i) = \text{Hash}(S \parallel B_i.\text{ID}) \times B_i.\text{Weight}$$
3. **选定最优节点**：选取评分最高的后端实例作为首选目标：
   $$B^* = \arg\max_{B_i} \text{Score}(S, B_i)$$

```
Client Request (X-Session-ID: "sess-abc")
            │
            ▼
┌─────────────────────────────────────────────────────────────┐
│                 HRW 亲和性调度器                            │
│  Backend 1 (权重 1.0): Score("sess-abc", B1) = 0.82 ──> 👑 │
│  Backend 2 (权重 1.0): Score("sess-abc", B2) = 0.43         │
│  Backend 3 (权重 0.5): Score("sess-abc", B3) = 0.61         │
└─────────────────────────────┬───────────────────────────────┘
                              │
                              ▼
                   分发给 Backend 1 (命中 KV Cache 显存)
```

#### 溢出保护与优雅降级（Spillover Protection）
- 若首选亲和节点当前并发数已达到 `max_concurrency` 上限，或者连续心跳探测失败被标记为 `unhealthy`；
- 调度器自动将流量顺延溢出（Spillover）至评分次高的健康后端，**绝不因为追求缓存亲和而让请求排队超时或失败**。

---

### 2. 实例级原子 CAS 无锁并发反压控制

为杜绝传统全局粗粒度限流无法保护物理算力卡的问题，CodeGate 实现了精确到每个物理后端实例的并发占槽机制：

```go
// 占槽伪代码实现
func (b *Backend) AcquireSlot() bool {
    for {
        current := atomic.LoadInt32(&b.activeConnections)
        if current >= b.MaxConcurrency {
            return false // 实例已饱和
        }
        if atomic.CompareAndSwapInt32(&b.activeConnections, current, current+1) {
            return true  // 成功占槽
        }
    }
}

// 释放槽位
func (b *Backend) ReleaseSlot() {
    atomic.AddInt32(&b.activeConnections, -1)
}
```

- **全流程防护**：请求到达时通过 CAS 占槽，请求结束（无论是正常完成还是客户端主动中断）在 `defer` 中释放槽位；
- **自适应负载均衡**：在执行“加权最少连接”调度时，根据当前活跃连接数与最大并发上限的比例动态评分，优先分发给水位较低的实例。

---

### 3. 默认模型容灾降级（Default Model Fallback）

当遇到大模型供应商晚高峰突发全线故障（如供应商返回 503/504、或实例全部被熔断）时：
1. 调度引擎感知目标模型可用后端列表为空；
2. 查询调用者配额策略中设定的 `default_model`（如 `deepseek-v3` 降级至 `qwen-2.5-72b`）；
3. 网关自动透明重写路由，将请求派发至备选模型的健康实例，下游研发系统（如代码扫描任务）无感平稳完成。

## 四、存储与高性能数据流设计

```
                      高频调用请求 (海量 QPS)
                               │
                               ▼
            ┌────────────────────────────────────┐
            │        本地内存缓存 (LRU Cache)    │
            │   (API Key 鉴权 / 用户策略数据)    │
            └──────────────────┬─────────────────┘
                               │ 纳秒级命中
                               ▼
            ┌────────────────────────────────────┐
            │     滑动窗口限流器 (内存时间环)    │
            │      Atomic CAS 活跃并发计数       │
            └──────────────────┬─────────────────┘
                               │
                               ▼
            ┌────────────────────────────────────┐
            │      批量异步持久化通道 (Channel)  │
            └──────────────────┬─────────────────┘
                               │ 定时 / 批量聚合 (Ticker)
                               ▼
            ┌────────────────────────────────────┐
            │     纯 Go SQLite 本地数据库        │
            │     (配置 / 账单流水 / 审计日志)   │
            └────────────────────────────────────┘
```

1. **纳秒级高频路径**：API Key 鉴权、速率计数、并发控制全部运行在内存数据结构中，请求处理阶段不发生同步磁盘 I/O。
2. **异步落盘路径**：消耗 Token 记录与 Access Log 通过缓冲 Channel 投递给异步工作协程，采用批量写入事务提交至 SQLite，避免多线程写锁竞争。
3. **日志自动轮转**：每日定时检查清理超过 `retention_days`（默认 7 天）的历史日志，确保本地单文件数据库大小稳定可控。

## 五、单二进制自包含交付原理

为了让 CodeGate 能够在企业内网任何一台干净的机器上“拉起即用”，系统采用彻底解耦外部环境的工程实践：

1. **前端工程构建与嵌入**：
   - 前端采用 React 18 + Vite 构建，产物编译至静态目录；
   - 后端通过 Go 1.16+ 引入的原生文件系统嵌入能力进行捆绑：
     ```go
     //go:embed all:web/dist
     var WebAssets embed.FS
     ```
   - Gin 路由接管静态资源请求，支持 SPA 单页应用的 HTML5 History 路由回退。
2. **纯 Go 编译无 CGO**：
   - 传统 SQLite（如 `go-sqlite3`）依赖本地 C 编译器动态链接 `glibc`，导致交叉编译复杂且跨 Linux 发行版极易出现 ABI 冲突；
   - CodeGate 采用纯 Go 翻译版本的 SQLite 驱动（`modernc.org/sqlite`），支持 `CGO_ENABLED=0`，可一键交叉编译至 Linux AMD64 / ARM64、macOS 以及 Windows。

## 六、配置热重载与生命周期管理

- **配置管理器（ConfigManager）**：系统在内存中维护全局配置单例，支持通过文件监听（fsnotify）或管理后台 API 触发热更新。
- **发布-订阅机制**：
  - 当模型增删、后端实例权重变更或限流阈值调整时，触发内部事件总线；
  - 调度器与限流器动态重构路由表，无须重启 HTTP 监听端口；
  - 正在进行中的数十个分钟级长流式生成连接（如大型代码生成）完全不受影响，实现真正意义上的 **Zero-Downtime** 运维。
